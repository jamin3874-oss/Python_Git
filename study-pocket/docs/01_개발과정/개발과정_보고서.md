# PDF 시험 공부 도우미를 모바일 학습 앱으로 발전시킨 과정

작성일: 2026-11-04. 실제 대화의 요구 변경과 기존 코드·검증 문서를 기준으로 재구성한 과정 보고서입니다. 과거 작업과 이번 작업을 구분하며, 과거 성능 수치는 이번 새 앱의 측정값으로 사용하지 않습니다.

## 1. 출발점: 강의 PDF를 읽어주는 AI

초기에는 Python 기반 `coastal_study_app/app.py`를 중심으로 해안·항만공학 강의자료를 정리하려 했습니다. 단순 텍스트 추출로는 손글씨, 그림, 수식을 놓칠 수 있어 PDF 페이지를 이미지로 만들고 Codyssey의 Claude 계열 모델에 전달하는 방식으로 발전했습니다. 사용자는 여러 PDF, 수백 쪽 자료, 개인적인 X 필기, API 연결을 주요 요구로 제시했습니다.

## 2. 실행과 API 키 관리

필요 라이브러리와 실행 스크립트를 정비하고, 실제 키를 소스에 넣는 대신 환경변수 또는 앱의 메모리 입력을 사용하는 방향으로 정리했습니다. PC 환경변수가 외부 사이트에 자동으로 전달되지 않는다는 점을 구분했습니다. 연결 확인은 단순히 키가 입력되었다는 표시가 아니라 실제 모델 응답을 받아 확인하도록 설계했습니다.

이 단계에서 배운 점은 비밀정보의 보관 위치와 실행 위치가 다르다는 것입니다. 로컬 앱, 서버 배포 환경, 브라우저의 현재 탭은 서로 별개의 환경입니다.

## 3. 과목 전용 도구에서 범용 학습 서비스로

사용자는 항만공학 전용 사이트보다 어떤 과목이든 사용할 수 있는 서비스를 원했습니다. 화면 문구와 AI 지시를 일반화하고, 사용자가 원하는 요약 방식·시험 범위·분량을 자유롭게 적을 수 있는 요청란을 추가했습니다. 대화 기능도 확장하여 자료 제작 후에 질문과 후속 설명을 이어갈 수 있게 했습니다.

## 4. 실제 강의자료와 작은 손글씨

사용자가 지정한 강의자료 두 개는 각각 47쪽과 49쪽, 합계 96쪽이었습니다. 텍스트 레이어만 보는 방식과 페이지 이미지를 보는 방식의 차이를 점검했습니다. 작은 필기는 전체 페이지 해상도를 무조건 높이기보다 필요한 영역을 원본 PDF에서 별도로 확대해 판독하도록 만들었습니다. 판독 결과를 사용자가 고칠 수 있게 해 잘못 읽힌 수치가 그대로 학습 자료로 확정되지 않도록 했습니다.

DPI를 높이면 픽셀 수·메모리·처리 시간이 늘어납니다. 전체 문서 읽기와 작은 필기 확대를 나누는 이유는 문맥을 유지하면서 필요한 부분에 해상도를 집중하기 위해서입니다. 이미지 분석이 모든 필기를 정확히 읽는다는 뜻은 아니며, 실제 인식률은 별도 평가가 필요합니다.

## 5. X 표시의 의미 수정

사용자가 말한 X는 OX 문항의 답이 아니라 개인적으로 시험 범위에서 빼려고 써둔 메모였습니다. 별도의 일괄 판정 과정을 강요하는 대신, “직접 X 표시한 부분은 제외해줘” 같은 자연어 요청을 전체 자료 처리에 적용하는 방식으로 바꾸었습니다. 수식의 x, 선택지의 X, 개인 제외 메모를 구분하도록 맥락을 함께 전달했습니다.

이 변화는 기술적 판정 기능을 늘리는 것보다 사용자의 실제 목적을 먼저 확인하는 것이 중요함을 보여줍니다.

## 6. 잘못 올린 자료를 지우는 흐름

PDF별 삭제와 프로젝트 전체 삭제를 추가했습니다. 파일명이 같아도 업로드된 파일 단위를 구별하고, 삭제 자료가 남아있는 노트·이미지·참고 사본과 함께 처리하도록 했습니다. 이번 제출용 앱에서는 PDF 삭제 시 그 자료가 섞인 통합 노트·중간 읽기·프로젝트 대화를 지웁니다. PC에 있는 원본은 건드리지 않습니다.

## 7. 읽기·저장 속도 개선

기존 웹 서비스에서는 페이지마다 따로 렌더링하고 업로드하는 비용이 컸습니다. 파일을 한 번 열고, 캔버스와 이미지를 재사용하고, 준비된 여러 페이지를 묶어 저장하도록 개선했습니다. 기존 기록의 로컬 측정에서는 실제 96쪽 준비·업로드가 약 33.172초에서 17.828초로 줄었습니다. 36쪽 저장 측정 중앙값은 11.450초에서 3.029초였습니다.

이는 당시 PC·로컬 HTTP·저장소를 이용한 측정이며 외부 서비스나 휴대폰의 속도를 보장하지 않습니다. 이번 새 앱은 한 단계 더 바꾸어 **원본 PDF를 기기에 저장한 뒤 필요한 페이지를 분석 시점에 렌더링**합니다. 전체 이미지 변환과 서버 업로드를 공부 시작의 선행 조건에서 제거했습니다. 이번 앱에 대한 동일 조건 속도 비교는 아직 수행하지 않았습니다.

## 8. 슬라이드별 수동 작업에서 전체 노트로

사용자는 슬라이드마다 버튼을 누르거나 생성 개수를 고르는 흐름 대신 전체 PDF를 한 번에 처리하기를 원했습니다. 전체 프로젝트를 하나의 작업으로 시작하고 여러 페이지를 자동으로 읽은 뒤, 관련 개념을 계층적으로 합쳐 하나의 노트를 만드는 방식으로 바꾸었습니다. 큰 PDF 전체를 무조건 단일 API 요청에 넣으면 입력 한도에 걸리므로 내부 묶음은 유지하되 사용자가 묶음을 수동 관리할 필요를 없앴습니다.

각 묶음의 결과를 저장하여 실패·중단 후 이어가고, 새 노트가 완성될 때까지 이전 완성본을 유지했습니다. 기존 호스팅 앱에서는 이 기능을 포함한 테스트 100개와 HTTP 검증 통과가 기록되어 있습니다. 이는 이번 앱의 41개 테스트와 다른 결과입니다.

## 9. 이번 과제용 구현: 공부주머니

첨부 과제의 순수 HTML/CSS/JavaScript, Python API 조건에 맞추어 별도 제출 프로젝트를 만들었습니다. 기존 React 기반 서비스와 자료를 보존하면서 새로운 앱을 분리했습니다.

- 자료실·통합 공부 노트·AI 대화의 세 화면을 중심으로 UI를 구성했습니다.
- 휴대폰에서 읽기 쉬운 레이아웃, 하단 메뉴, PWA manifest·아이콘·서비스 워커를 추가했습니다.
- 공개 배포 시 사용자마다 개인 키를 쓰고 기기별로 자료를 보관하도록 했습니다.
- Vercel용 Python API와 로컬 실행 서버를 만들었습니다. 추가로 같은 프론트를 실행하는 Sites 호스팅 어댑터를 준비했습니다.
- 전체 노트 처리기를 UI와 분리하여 501쪽 자동 처리와 중단·복구를 모의 API로 검사했습니다.

## 10. 검증과 남은 작업

이번 앱은 JavaScript 27개·Python 14개 자동 테스트, 로컬 HTTP 검사를 통과했습니다. 실제 유료 API 호출은 하지 않았고, 휴대폰 설치·터치 동작·모델의 실제 판독 정확도는 아직 실기기 검증이 필요합니다. 브라우저 제어 도구가 현재 URL을 확인하지 못해 화면 조작 검증이 중단되었습니다.

GitHub/Vercel은 사용자가 기존 주소를 전달하기로 했으며 연결 단계가 남아 있습니다. 공개 접근 설정도 명시적인 공개 승인이 필요한 상태입니다. 배포 플랫폼의 상태와 미완료 항목은 배포현황 문서에 따로 기록합니다.

## 회고

이 프로젝트에서 AI는 코드를 작성하는 도구이면서, 학습 자료를 읽어 학습자와 대화하는 서비스의 핵심 기능이기도 했습니다. 사용자의 반복적인 피드백으로 범위 판정, 처리 단위, 키 관리, 저장 방식이 달라졌습니다. 유용한 결과를 만들려면 “AI가 읽는다”는 주장보다 어떤 입력을 보내고, 어떤 부분을 저장하고, 무엇을 실제로 검사했는지 구체적으로 남겨야 한다는 점을 확인했습니다.
